# 宿主页面 BFF 审查

日期：2026-10-09。客户端基线：`e56bad1`；服务端基线：`e9bae8a`。

本次逐页检查宿主、页面弹层、客户端数据层，以及对应 Worker / Durable Object 实现。以下结论来自代码静态审查，未采集手机网络瀑布或线上延迟；请求数描述的是代码路径，收益需实测。应用自身业务接口不在本次范围内。以下“现状”保留审查基线；用户确认后已实施，完成情况见下节。

## 实施结果

- 发现页改用 `/v1/discovery`，批量返回讨论、互动计数和关注状态，保留完整预载清单；互动分区失败时仍返回作品。关注按钮缺缓存时只读取 relationship。
- 作品评论通过 appId 一次读取讨论和评论第一页；面板复用刚返回的首屏，后续分页和写接口保持原契约。原有空评论定位与关注按钮布局保留。
- 制作进度使用 progress 动作，仅传本轮最后模型回复。摘要按会话、轮次和上游版本持久缓存；版本不变不再遍历历史。首次生成或上游版本变化仍可能扫描，失败返回本轮已知回复并标 stale，不创建轮询。
- “我的”通过 `/v1/me/works` 共用摘要与每页 24 个作品，批量读取展示元数据，不把制作凭据逐条写入本地再读回。新提交的本地轮次、实际运行版本覆盖展示；制作恢复保留原接口，进入制作时按需调用。手动刷新保留上游同步语义。
- 作者页使用 summary/posts/apps 投影与独立游标；关注关系不拉隐藏列表，公开作品数量使用 totalCount。搜索和关联作品选择器采用轻量投影，详情补齐后才允许需要完整清单的操作。
- 作品顺序、作者、分类及中文子串搜索使用既有 Workshop SQLite 的派生索引；关注/作者动态与通知分类使用既有 Posts SQLite 的索引。旧数据首次回填，发布、撤回、关注、删除与原记录在同一事务维护，没有新增绑定或删除原始数据。
- 常用接口补齐最新名称、简介、版本和可用性，撤回作品仍保留收藏快照；打开时继续核对公开版本。本机安装列表使用已有同步 MMKV 读取，避免反复 await 同一条元数据。
- 私信事件携带 peerId，可见会话定向读取增量，超过一页继续按增量边界取下一页；已读以实际可见消息为边界。WebSocket 失败时，两个计数 HTTP 合并为账号计数摘要。
- 关注列表消费写响应局部更新。AI 引擎保存/删除后在宿主更新不含密钥的显示元数据，匹配既有原生默认项规则，通常不再重复跨桥读取；保存响应缺少 ID 时保留兼容回读，不需要升级 APK。

验证：服务端新增 `tests/pageReads.test.mjs`，使用真实本地 SQLite 检查搜索、回填、游标、事务回滚、超过 5000 条动态的稀疏关注流、聚合失败降级、账号隔离、旧作品恢复契约、进度缓存与私信增量。客户端随宿主构建验证；未把本地回归结果当作手机帧率或线上延迟测量。

## 优先处理的四处

### P1：发现作品，把互动和关注状态随作品分页返回

现状：

- `ApplicationFeedScreen.tsx` 调用 `fetchMarketPage`，每页 24 个作品。
- `ApplicationInteractions.tsx:47` 的 `read()` 为当前作品另外调用 `/v1/application-discussions/:appId`；切换回来还会静默刷新互动。
- `AuthorFollowButton.tsx:23` 在登录且关注状态缓存缺失时调用 `fetchAuthorProfile`。
- `posts.ts:308` 的作者主页同时聚合作者资料、公开作品列表、动态第一页和关注统计。小加号只需要一个布尔值，却拉取了整个主页。
- `posts.ts:738` 的作品讨论接口又回调 Workshop 的 `market?appId=...&detail=1`，取客户端列表已经拿到的作品信息。

因此，新浏览 N 个作品，可能增加 N 次讨论请求，以及 U 次完整作者主页请求；U 为尚无关注缓存的不同作者数，游客没有作者关注状态请求。这里还不包括 bundle、图片和资源下载。

建议：给发现页增加专用分页投影，返回作品清单和展示信息，以及 `discussionId`、点赞数、评论数、`liked`、`saved`、`authorFollowing`。在现有 Worker 入口组合 Workshop 与 Posts，Posts 对一页 appId / authorId 去重后批量取元数据。公开作品和账号互动分开缓存，再按当前账号组装结果；不要对每一条内部调用现有单作品讨论接口。

讨论身份沿用现有按 appId 建立的身份，确保跨版本讨论连续；未初始化的讨论可以在需要读取评论或写互动时创建。BFF 不预取评论正文、不执行作品代码，也不替代原生资源下载队列。后续互动按实时事件、明确刷新或合理新鲜度更新，避免只返回一次快照后永久过期。

预期：分页返回后可以直接绘制当前页及后续作品的互动和关注状态，消除为了底部栏逐条补请求的模式。作品初始加载、下载和 UI 执行仍需分别测量。

### P1：作品评论，合并冷启动的讨论定位与评论第一页

现状：`ApplicationInteractions.tsx:15` 的 `readApplicationComments` 在缓存未命中时先请求讨论；评论面板挂载后，`ApplicationCommentsSheet.tsx:95` 再请求 `/v1/posts/:discussionId`。冷路径有两个有依赖的 HTTP 往返；互动已经就绪时只需后一个请求。关注缓存也可能触发完整作者主页请求。

建议：支持按 appId 一次返回讨论、评论第一页、游标及作者关注状态；已有作品展示快照可以立即显示，响应再更新。后续评论分页只返回这一讨论需要的内容，不重复获取主页。发送、删除继续让写接口返回更新后的计数和实际评论，复用现有行为。

预期：冷开评论从两个串行数据请求变为一个；不预取隐藏评论，不把全部评论放进发现页列表。

### P1：制作进度，直接返回大阶段和最后一条模型回复

现状：`jolly/progress.ts:129` 请求 detail，`:137` 的 `while (cursor)` 继续逐页调用 history，然后在客户端筛出最后一条模型回复。`cloudEvolve.ts:204` 的 history 每一页都会访问 `/v1/workshop`。界面只展示三个大阶段和最后回复，却仍下载完整历史。

注意：`loadJulesRun()` 主要是本地存储读取，不能把它们误算成多次网络请求；缺少会话关联时 `loadJulesSession()` 才可能触发 `/v1/works` 恢复。服务端已有活动页缓存和 compact 路径，但当前进度页仍会追完历史分页。

建议：新增宿主进度摘要读模型，按 appId 和制作轮次返回 `state`、交付状态、必要作品信息、`lastModelReply`、`updatedAt`、`stale`。客户端进度页不再请求历史分页。完整日志能力仍可保留给其他现有调用者，避免破坏 SDK 兼容。

不能仅把客户端 while 循环搬到服务端后让每次请求继续全量扫描。应复用活动缓存或按制作轮次增量归并最后回复；若上游不能倒序查询，首次回填仍可能扫描，但后续摘要读取不重复传输全部历史。跨轮次数据必须隔离，不能把旧任务回复当成本轮回复。

预期：客户端进度读取从 `1 + 历史剩余页数` 次 HTTP 变为一次摘要请求，显著减少 JSON、传输和 JS 处理；第一次摘要生成的上游耗时需要独立测量。

### P1：我的，把统计与作品首屏合并，停止为统计加载主页全文

现状：`MyProfileScreen.tsx:104` 为作品数、粉丝数、关注数请求完整作者主页；默认作品页还在 `MyApplicationsScreen.tsx:124` 读取本机安装，再等待 `restoreWorks`，随后将云端结果写入多处本地存储，再读回拼装展示。

服务端 `/v1/works` 已聚合候选版本、上架状态和制作状态，不存在客户端逐作品请求状态的问题；需要优化的是重复读模型和传输。`index.ts:973` 当前返回全部作品，每条还重复携带恢复/制作所需字段，且按作品进行多轮存储读取。手动 refresh 会触发未完成任务的状态同步，并最多等待 6.5 秒。

建议：提供账号主页摘要＋作品分页，返回真实总数、粉丝/关注数、首屏作品展示字段与状态。统计不依赖动态第一页。列表渲染直接消费结构化快照，本地草稿、已安装/已运行状态在客户端覆盖；制作恢复凭据和完整清单按必要流程单独读取或复用现有接口。不能让每次进“我的”都等待全部活动任务同步，保留静默更新与手动刷新语义。

预期：减少首屏两个重叠的页面读请求，以及云端数据“写散再读回”的本地串行处理。后一部分属于客户端数据层优化，不能单靠 BFF 解决。

## 跨页面问题

1. **服务端有聚合，但内部仍可 N+1。** `posts.ts:760` 的单条 decorate 串行读取 stats、liked、saved，可改成一个批量 storage.get；详情的评论、作者水合和统计也有可并行部分。聚合 discovery 时必须批量读，不能循环调用 decorate 或作者主页。
2. **作者主页副作用过重。** 作者主页内部直接调用动态列表，而动态列表会执行 recordViews。因此为了关注小按钮或“我的”统计加载主页，还会把并未展示的动态纳入 API 交付曝光记录。轻量关系/摘要接口可同时消除这类副作用。
3. **全量扫描会限制增长。** `index.ts:797` 的 market 先读取全部 shared 作品，在内存筛选、排序、分页；`posts.ts:274` 的关注/作者动态可扫描到 5000 条。通知分类也在统一通知序列中过滤。这些需要发布顺序、作者、分类或关注流索引，不能用更大的返回包掩盖。
4. **作者公开作品缺独立分页契约。** `/profiles/:id` 内部 market 的 authorId 查询当前使用全列表契约；若作者作品变多，主页、关注小按钮和“我的”统计都会越来越重。应提供真实 totalCount 和作品游标，不能再把数组长度当作未来分页后的总数。
5. **聊天实时刷新粒度过大。** `useInboxVersion(true)` 接受任意 message 事件，而当前分发的事件没有会话标识；可见聊天可能因别的会话消息而重拉当前消息页。应携带会话标识/变更版本并定向拉增量。已读以实际可见消息边界为准，不能为了少一次请求把加载历史当成已读。
6. **瘦身优先于把所有数据塞进一包。** 搜索、选择作品、统计只需投影；发现页保留资源预载必需的 manifest。发布图、录音、bundle 等独立资源继续走原有下载/CDN 路径，不内联进 JSON。

## 实施顺序与验证

第一批：发现页分页互动＋关注、作品评论首屏。第二批：制作进度摘要。第三批：“我的”摘要＋作品分页。第四批：轻量作者页/作品选择器、HTTP 未读 fallback 和服务端索引。

客户端和服务端同步演进，保留原读接口以兼容旧动态包；已有 SDK 公共契约和本机安装/运行判断不改变。

每一批验证三类指标：设备实际 HTTP 数与串行轮次、响应字节和 JSON 处理量、Worker 内部 DO 调用/存储扫描量及首屏可交互时间。分别测试游客/登录、冷缓存/回访、关注变化、作品撤回、切换账号、失败重试。聚合接口不能让一个非关键分区失败拖垮整页，也不能预先加载未访问的 tab。
