# 独立应用 SDK 与打包方案（第一版）

状态：技术方案，尚未实现。本文中的接口、清单和目录均为拟定设计。

## 目标与取舍

让 AI 在独立应用工程中开发，将应用发布为独立包，由宿主安装和加载；新增、更新一款应用不要求重发宿主。宿主升级时，只影响实际依赖了不兼容能力的应用，不按整份 vendor 哈希作废所有包。

平台是通用宿主壳，Jolly 也按独立应用交付，并在首次安装时默认安装。Jolly 不作为宿主业务代码，也不采用专用的打包或加载流程。

首版采用：一个共享 RN/Hermes 环境、一个版本的共享依赖、每款应用一个包、每款应用同一进程只运行一个版本。应用间不建立依赖，不做依赖版本运行时协商、无感热替换、多套 vendor 或任意代码沙箱。源码先保留在同一仓库，工程和产物独立即可。

## 参考成熟系统

- VS Code：使用 manifest 声明入口与宿主 API 版本要求，公共 Extension API 与宿主实现分开。借鉴其声明式入口、版本要求和生命周期；不照搬独立 Extension Host，因为我们的 React 页面直接参与宿主渲染。参考：https://code.visualstudio.com/api/references/extension-manifest ，https://code.visualstudio.com/api/ 。
- IntelliJ：插件声明支持的平台版本范围，不把兼容性默认扩展到所有未来版本。借鉴加载前兼容检查、发布前兼容检查和升级前迁移。参考：https://plugins.jetbrains.com/docs/intellij/build-number-ranges.html 。
- webpack Module Federation：明确区分私有依赖和共享依赖，通过共享作用域管理版本。借鉴共享实例与唯一身份；首版不引入它的运行时版本选择、回退和容器依赖机制。参考：https://webpack.js.org/concepts/module-federation/ ，https://webpack.js.org/plugins/module-federation-plugin/ 。

下面的设计是针对当前 RN/Metro 架构的选择，不是上述系统现成提供的 RN 实现。

## 一、三个边界

| 边界 | 包含什么 | 应用如何使用 |
| --- | --- | --- |
| 平台运行环境 | RN、Hermes、原生模块、共享第三方库、SDK 运行实现、宿主 | 由平台发布 |
| SDK 开发套件 | 类型、允许的公共入口、固定工具链、模板、文档 | AI 开发工程的依赖 |
| 独立应用 | 页面、动态卡片、业务逻辑、私有纯 JS 依赖、资源 | 独立构建、发布、安装 |

物理运行包先保留 vendor + 宿主两层。SDK 运行实现随宿主加载，不为 SDK 新建第三个发布通道。宿主初始化 SDK 后才能加载应用。SDK 开发包只包含开发所需内容和适配入口，应用不能打入第二份 SDK 注册表或状态容器。

原生层负责经过校验的文件下载、缓存和分包执行。RN 层负责应用定义、实例上下文、页面、动态卡片和业务生命周期。服务端只负责不可变发布记录与授权，不参与应用业务执行。

### Jolly 默认安装与宿主职责

宿主保留通用导航、应用列表、动态时间线、安装更新管理、设置、权限与错误恢复界面。Jolly 拥有心愿输入、AI 伙伴形象、制作进度、工坊页面及自身动态卡片；宿主不再管理它的提示词、会话 UI 或制作状态。

平台提供受授权的 `creation` SDK 服务：创建/恢复/停止制作会话、查询交付状态、加载目标应用版本、由用户明确确认收下。Jolly 通过该接口完成业务，不访问宿主内部存储或直接持有 Jules/GitHub 凭证。会话归属、并发限制和版本确认仍由服务端执行；确认核对目标作品的 releaseId，而不是 Jolly 自身版本。

服务端及宿主按平台授权授予制作能力，首版授权给默认 Jolly 应用；不能仅凭应用在 manifest 中声明就获得权限。SDK 服务接口不硬编码 Jolly 页面或形象，后续可授权其他制作应用。

默认应用用一份平台 bootstrap 清单声明，不在运行时业务 registry 中硬编码。为保证首次启动离线可用，APK 携带经过校验、兼容的 Jolly 种子包，使用与其他应用相同的安装记录、资源目录和加载器初始化；它是内置安装资源，不并入 vendor 或宿主模块。

bootstrap 只在首次初始化时应用，后续 Jolly 通过普通应用更新流程升级。默认安装不等于强制常驻：用户停用或卸载后保留该选择，不在每次启动时自动装回。重新添加和故障恢复由宿主通用应用管理入口提供，不依赖 Jolly 正常运行。初始导航入口由 bootstrap 指定已安装应用，导航到它仍通过通用应用路由。

Jolly 使用相同的存储隔离、生命周期、版本兼容和回滚机制。迁移现有工坊时保留待确认会话、授权关联和制作动态身份；更新 Jolly 不得丢失正在进行的制作。

## 二、共享依赖通过公共入口连接

应用可以正常 import React、React Native 和平台已支持的第三方 RN 库，例如 `react-native-svg`，不要求所有库都经过 SDK 二次封装。

平台建立一个显式的公共模块表，逻辑上类似：

```ts
publicModules = {
  "react": React,
  "react/jsx-runtime": ReactJsxRuntime,
  "react-native": ReactNative,
  "react-native-svg": ReactNativeSvg,
  "@zijinhua/app-sdk": AppSdk,
};
```

实际实现要保留库的默认/命名导出语义，通过构建生成的 CommonJS 适配模块导出原始模块对象；不要复制导出并制造第二份单例。平台注册表在进程中只初始化一次。公共入口按需登记，应用使用 JSX 和编译器生成的入口也必须被覆盖。

应用构建时，Metro 对声明的共享入口解析到适配模块，适配模块通过公共入口名取平台模块。应用包不直接引用 vendor 或宿主的内部模块编号，也不打入这些共享库的实现。

这样平台仍可使用自己的 Metro 编号体系；应用看到的是 `react-native-svg` 这个公共契约。vendor 内部编号或物理路径变化本身不影响应用，公共库 API 和原生 ABI 是否兼容仍需单独检查。

未公开的第三方内部路径默认不允许；确有需要的官方子入口应单独纳入公共入口表。禁止引用宿主源码和直接原生桥接。构建工具拒绝非法导入，并拒绝私有依赖间接携带第二份 React/RN。

### 依赖分类

| 类型 | 首版策略 | 变化的影响 |
| --- | --- | --- |
| React、RN、SDK，以及需要共享状态的库 | 平台共享，应用不得自带另一份 | 不兼容变化需迁移相关应用 |
| 带原生实现的 RN 库 | 平台共享，只能用公开支持的版本与入口 | 新增原生能力需要新 APK；旧 APK保留兼容旧应用 |
| 无原生实现、无平台单例要求的纯 JS 库 | 默认随应用私有打包 | 只影响该应用，无需改 vendor |
| 应用业务模块与资源 | 应用私有 | 只影响该应用 |

原生库的 JS 与原生部分应作为一套兼容组合处理，不能只更新 JS。第三方库版本范围不等于经过验证的兼容性保证。

## 三、首版构建与包格式

每个应用输出一份 manifest、一份 Hermes 字节码包和资源文件。卡片与页面共用这一个包，页面模块延迟执行。暂不拆 cards/main 两个包。

继续复用 Metro 与现有 Hermes 编译流程，不引入第二套编译器。新增 application 构建模式：

1. 读取工程锁文件和平台开发契约，确认工具链与共享依赖。
2. 为共享入口生成适配模块，构建应用及其私有依赖。
3. 应用私有模块使用平台分配的编号范围，避开 vendor/宿主及其他应用。
4. 生成 JS、源码映射，编译与目标运行环境兼容的 Hermes 字节码。
5. 收集资源、计算哈希与大小，生成发布清单。
6. 先上传包体和资源，全部成功后发布不可变版本记录。

模块编号范围由平台持久化分配，绑定 appId；本地开发使用注册后获得的开发配置，不依赖每次在线分配。范围不能被应用任意声明。工具生成范围内的稳定编号表，并检查容量及 Metro/Hermes 支持的数值边界。宿主/vendor也必须限制到保留范围。相同应用的多个版本复用范围，但不允许在同一进程混装。

示意清单：

```json
{
  "format": 1,
  "appId": "pomodoro",
  "version": "1.0.0",
  "releaseId": "<发布内容哈希>",
  "requires": {
    "engineAbi": "<RN/Hermes运行兼容代号>",
    "sdk": "^1.0.0",
    "shared": { "react-native-svg": "<实际要求版本>" }
  },
  "bundle": { "sha256": "...", "bytes": 12345 },
  "assets": [],
  "dataSchemaVersion": 1,
  "source": { "commit": "...", "dirty": false },
  "builtWith": {
    "toolchain": "...",
    "vendorHash": "...",
    "sdkHash": "..."
  }
}
```

`requires` 决定可否运行，`builtWith` 仅供复现与排查；不要求整份 vendorHash 相等。共享依赖清单由构建工具按实际导入及间接依赖生成，首版默认使用精确版本，不能由 AI 随意放宽。

engineAbi 覆盖字节码格式、RN 运行接口与基础原生 ABI 的兼容边界；不能只检查 SDK 版本而忽略 Hermes 字节码兼容性。该代号由维护者发布，不使用任意一次 APK 构建哈希代替。

资源需覆盖 RN 的静态 require 图片、尺寸信息和离线路径解析；第一版使用不可变内容哈希文件，由宿主解析本地安装路径，不写机器绝对路径或可变远程 URL 到应用包。

## 四、依赖变化后的规则

首版只保留三个运行兼容维度：engineAbi、SDK 版本、实际使用的共享库版本。业务数据版本单独用于迁移，不参与平台依赖协商。

| 变化 | 处理 |
| --- | --- |
| 宿主 UI 修改、平台内部重构、vendor 内部模块路径或编号变化 | 公共入口及兼容契约不变则旧应用继续运行 |
| SDK 增加接口 | 小版本升级；旧接口保留，旧应用可继续运行；使用新接口的新应用声明最低版本 |
| 新增共享库或原生能力 | 原有应用不受影响；新应用按要求筛选手机，必要时提示升级 APK |
| 应用私有纯 JS 依赖升级 | 仅重建该应用 |
| 共享第三方库升级 | 先评估实际引用该库的应用；首版默认要求重建这些应用，未使用该库的应用不受影响 |
| SDK 删除接口或改变已有语义 | SDK 大版本升级，提供迁移并重建受影响应用 |
| RN/Hermes 不兼容升级 | engineAbi 升级，可能需重建所有 RN 应用，这是基础运行环境变化的真实成本 |

不要仅因第三方补丁版本宣称兼容。后续有明确兼容证据时再扩大受支持范围；首版采用精确匹配使行为可预测。

### 平台升级流程

发布新平台前，从应用清单列出受影响范围，构建并准备新兼容版本，再开放平台升级。应用的新旧产物均保留，安装服务按手机契约选择最新兼容版本，不能让旧手机收到无法执行的新包。

本机切换新平台与相关应用版本应作为一次激活操作：文件全部准备好、兼容性检查全部通过后才切换安装快照；缺包时继续使用旧平台组合。回滚保留上一快照，不使用“先升级宿主，再逐个修应用”的半兼容状态。

前期规模小，维护者可以手动执行受影响应用重建；无需先建设自动迁移调度平台。但识别受影响范围、保留旧版本和加载前拒绝不兼容包是首版必需能力。

## 五、SDK 入口与生命周期

应用导出定义，由宿主调用 SDK 注册；导入应用模块不产生欢迎动态、不请求权限、不启动后台任务。

```tsx
export default defineApp({
  main: () => require("./app").default,
  cards: { welcome: WelcomeCard, activity: ActivityCard }
});
```

宿主为应用提供 AppContext：

- storage：限定当前实例的键空间，不读取其他应用或宿主内部键。
- feed：自动绑定当前实例身份，内容由应用自行绘制。
- navigation：返回、打开自身页面等公开导航操作。
- phone：当前实例允许调用的平台能力；实际调用时处理权限。
- creation：被平台授权的制作应用可使用的会话与交付服务；默认 Jolly 使用它，服务端保留最终授权和版本核对。
- 生命周期：安装、激活、停用；注册的订阅和计时器统一加入 disposable 清理列表。

加载模块、登记定义、激活、渲染页面分别记录日志。首次动态或页面需要应用时才加载包，同一进程同一应用只执行一次加载，并发请求共用同一个 Promise。加载成功必须收到对应 appId/releaseId 的登记结果，错误和超时要可定位。

停用会卸载页面、取消 SDK 托管资源，但不会声称已经卸载 JS 模块。更新和卸载后的代码清理由运行环境重启完成。React 错误边界只隔离渲染错误，严重 JS/原生错误仍可能影响宿主。

## 六、安装、更新与数据

安装状态保持简单：未安装 → 下载中 → 已安装；下载失败不改变现行版本，错误作为独立结果保存。已安装记录包含 appId、instanceId、activeReleaseId、pendingReleaseId 与上一版本。

首版同一 appId 只安装一份实例。安装包与个人数据分开；更新保留实例身份，卸载默认保留数据，删除数据是明确的独立操作。由其他应用改造出的作品使用新 appId，不覆盖原作品。

首次添加可以在现有运行环境按需加载。更新在重载时激活，禁止把新旧模块注入同一应用运行会话。新版本失败时返回上一兼容版本，连续失败后停用并展示错误，不无限重试。

数据迁移独立于代码切换：迁移前备份该应用数据，迁移失败恢复数据；回滚代码时同时处理数据版本。第一版只允许通过 SDK 管理的存储迁移，不能保证应用写到任意外部位置的数据可以自动恢复。

## 七、给 AI Coding Agent 的工程

```text
application/
  AGENTS.md
  package.json
  package-lock.json
  app.config.ts
  platform.lock.json
  src/index.ts
  src/app.tsx
  src/cards.tsx
  src/storage.ts
  assets/
```

包含 SDK 类型与可解析的适配入口、支持的共享库及精确版本、锁定工具链、示例应用、开发规则。AI 不需要 APK/server 或完整宿主源码。

`npm run publish` 完成必需构建、导入与兼容性校验、上传和清单发布，输出 appId/releaseId/sourceCommit。发布权限由服务端绑定目标应用，不能由本地 manifest 自行证明。保留源码映射，以 appId/releaseId 查到具体源码提交。

应用发布不再要求包含全局宿主线上 source.commit，而是遵守该应用的交付提交与平台开发契约；工坊收下只核对正在运行的应用 releaseId 与本轮候选，不依赖 PR 或 main。宿主继续使用自己的发布基线，两个流程不混用。

## 八、首版交付清单与顺序

1. SDK 与开发契约：AppContext、defineApp、公共模块表、第三方依赖清单、版本字段及导入边界。
2. 独立构建：Metro application 模式、共享适配入口、私有纯 JS 依赖、编号范围、字节码与资源产物。
3. 原生加载：应用包缓存与校验、按 appId/releaseId 加载、安装快照和重载激活；需要新 APK。
4. 宿主接入：用安装记录代替业务硬编码 registry，按需加载页面与自绘动态卡片；增加 bootstrap 默认安装与通用恢复入口。
5. 发布接入：应用版本记录、最新兼容版本选择、应用级权限和工坊版本确认。
6. 将 Jolly、记事本、番茄钟全部迁移为独立应用，保留现有用户数据、应用身份及工坊会话；首次安装默认提供 Jolly，形成最小端到端示例。

首版不交付市场搜索/推荐/社交 UI、应用间依赖、运行时依赖协商、同应用多版本并行、多个实例、后台热替换、通用数据迁移平台和恶意代码自动审核系统。

## 九、验收场景与排查

实现时应覆盖：两应用模块不冲突；只更新一个应用；依赖不同私有纯 JS 版本；共享库版本不匹配；平台新增无关库；SDK 向后兼容更新；engineAbi 不兼容；下载中断与哈希失败；资源离线加载；数据迁移失败；应用激活与重载回滚。这些是目标验收场景，当前实现范围和暂未支持的能力见 app-sdk-usage.md。

每一步统一记录 appId、releaseId、platformVersion、阶段和错误码，输出“缺哪一个接口/版本”，避免笼统“加载失败”。按发布版本保存 manifest、锁文件、工具链标识与源码映射，保留可导出的诊断记录。

SDK 边界和构建检查是合作应用的工程约束，共享 JS 环境不构成恶意代码安全沙箱。当前开发阶段由开发者体验收下后决定上架；未来 AI 恶意代码检测另行建设；开放不可信上传需要另设计安全隔离。
