# 市场信任与发布流程

采用同一个 RN/JS 环境。appId 只用于模块、数据和业务归属，不能证明调用者身份或隔离恶意代码。公开执行版本依赖维护者检查源码、依赖和产物后批准；作者候选仅用于本人明确信任后的体验。宿主确认需求制作、停止、候选体验、收下及市场变更。不要把这些确认描述成进程沙箱。

需求由登录账号提交；requestId 幂等创建，服务端在调用 Jules 前保存任务，响应丢失时按唯一会话标题接回。GET /v1/works 只返回当前账号的作品、会话与作品凭据。手机登录凭据保留在安全存储，Jolly 存储和订阅按账号分开；旧本机记录仅在 ownerId 相符时迁移。默认每账号每天 10 轮，同时最多 3 个制作任务，短事务预留额度。工坊按应用串行，外部请求不会阻塞公共市场读取或其他应用；验证码按邮箱串行，限额在存储事务中更新。

每轮发包使用 HMAC 授权，绑定 appId、ownerId、轮次和 7 天有效期；工作状态改变后撤销。SDK 1.1.4 将授权保存到 Git 元数据，通过 /v1/application-blobs/<id>/<sha256> 校验内容哈希并上传，再通过 /v1/catalog 原子比较 candidate 基线。source.commit 必须对应真实、干净的源码提交；vendor 稳定键与兼容检查继续执行。原作复制绑定 originalReleaseId 和 originalCommit，init 读取锁定提交中的 src/assets。

候选 → 作者加载体验 → 确认收下并核对 PR → accepted → 作者提交市场审核 → 维护者批准 → public。审核中的新版本不替换已有公开版本。审核记录绑定不可变 releaseId、包哈希与源码提交；旧官方公开快照作为已维护版本保留，社区快照须逐版本审核。已安装且曾审核通过的包允许离线启动；新的候选权限核对发生网络故障时保留待加载记录，明确失去归属或权限时才回退公开版本。卸载与撤回不清除业务数据。

加载阶段保留上一版和待确认记录，页面首次成功挂载后确认健康。模块求值或页面首次加载中断，下次启动拒绝失败版本并恢复旧包；页面运行报错时有旧包就切回并重载 JS，首装失败隔离该版本并重载，保留错误等待新包，避免重复执行失败版本。

## 升级与维护者操作

1. 提交平台源码，执行 npm run pack:sdk，上传不可变 tarball；更新 zjh-plugin SDK 固定地址和锁文件并提交。先公开 SDK 产物，避免云端升级到不存在的地址。
2. 构建新宿主与 Jolly 候选并检查配套 /v1/runtime 契约；共享库和 SDK runtime 仍为 1.1.0，无需仅为工具补丁更换 APK。发布前检查 Git 工作区干净和线上提交基线。
3. 协调部署服务端、新宿主和 Jolly 官方公开版本。服务端不再接受旧全局 PUBLISH_TOKEN/BUNDLE_CATALOG_TOKEN；升级期间停止旧工具任务并让旧手机更新后再创作。已有账号作品可接回；创建结果不明确时不重复创建。
4. **撤销旧云端共享 R2 凭据并从 Jules 集成环境删除它们。** 禁用新会话环境变量不能收回历史任务已得到的密钥；旧会话继续运行前应清除环境或迁移会话。Jules/GitHub 集成仅开放 zjh-plugin，服务端管理与维护者凭据不进入任务。
5. npm run review:applications 查看审核队列。人工检查 releaseId 对应的源码、依赖和 bundle 后，执行 npm run review:applications -- <appId> <releaseId> --approve；拒绝或撤销批准使用 --reject。官方公开发布仍通过 release:official 明确指定版本，不由云端自动执行。

这些步骤包含外部部署和凭据撤销。代码检查成功不等于线上已完成升级，也不能替代维护者的版本审核。
